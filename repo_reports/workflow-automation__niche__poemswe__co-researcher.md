## 1. Overview

`poemswe/co-researcher` is a cross-CLI “agent pack” that turns Claude Code, Gemini CLI, Codex, and OpenCode into a structured academic-research assistant by installing command wrappers plus role-specific skill prompts. A user runs commands like `/research`, `/analyze`, or `/methodology`, which dispatch into specialized skill files rather than a compiled Python/JS agent runtime (`commands/research.md:1-6`, `commands/methodology.toml:1-2`). The output they get is guided, methodology-heavy research deliverables (e.g., task plans, literature reviews, validity checks, synthesis) generated by the host LLM while following the skill protocol (`skills/research-manager/SKILL.md:12-76`, `skills/literature-review/SKILL.md:42-73`). The repo also ships an eval harness that benchmarks those skill prompts by executing them through external CLIs and scoring responses (`evals/run_eval.py:10-17`, `evals/lib/core.py:172-223`).

## 2. Agent Framework & Architecture

No mainstream agent framework (LangGraph, CrewAI, AutoGen, LangChain) is actually implemented in source code; there are no such imports in executable files. The architecture is **custom prompt-driven orchestration**: commands are thin dispatchers that tell the model to “invoke skill X and follow it exactly” (`commands/research.toml:1-2`, `commands/analyze.md:1-6`), and each skill defines role, protocol, tools, and output contract in Markdown frontmatter + structured sections (`skills/research-manager/SKILL.md:1-10`, `skills/research-methodology/SKILL.md:48-76`).

The “intelligence” mainly lives in these skill specs, especially `research-manager`, which acts as a planner/PI role and instructs dynamic task scaffolding, dependency-aware execution, and delegation to other specialized skills (`skills/research-manager/SKILL.md:36-61`). Installation/plugin code mainly injects bootstrap instructions and exposes skills, not runtime planning algorithms (`.opencode/plugins/co-researcher.js:29-77`, `.codex/co-researcher-codex:108-155`).

A secondary architecture piece is the Python evaluation runner: it programmatically loads skill text, wraps it into an execution prompt, calls provider CLIs, then runs judge-model scoring over rubric profiles (`evals/lib/core.py:215-223`, `evals/lib/core.py:247-303`). That is test orchestration, not production agent orchestration.

## 3. Orchestration Pattern

Closest match: **hierarchical (manager-worker), prompt-level**.

Control flow is explicitly manager-first: `/research` always routes to `research-manager`, which performs scoping, generates phased tasks, persists them, then executes first unblocked tasks via delegated specialist roles (`commands/research.md:1-6`, `skills/research-manager/SKILL.md:36-61`).

```39:61:skills/research-manager/SKILL.md
1.  **Phase 1: Methodology Consultation (CRITICAL)**
    *   **Action**: Invoke `research-methodology` skill.
...
2.  **Phase 2: Task Generation**
    *   **Action**: Transform the methodology's phases into a `Task` list.
...
### 3. Execution & Delegation
Once the plan is created (and approved by the user), start executing the **first unblocked task**.
*   **Delegate**: "I am now acting as the [Skill Name] to complete Task [X]..."
```

Platform commands are wrappers that enforce this routing model:

```1:2:commands/research.toml
description = "Start a research project with intelligent agent orchestration"
prompt = """Invoke the co-researcher:research-manager skill and follow it exactly as presented to you: {{args}}"""
```

So orchestration is not a graph/state-machine library; it is a manager prompt that governs sequential dependency-aware delegation.

## 7. Strengths, Limitations & Research Relevance

- **Strengths:**
  - Strong separation of roles via specialized skill files with explicit protocols and output schemas (`skills/*/SKILL.md`).
  - Clear manager-worker orchestration logic in `research-manager`, including dependency-aware execution and persistence fallback.
  - Cross-platform packaging (Claude/Gemini/Codex/OpenCode) with consistent command semantics (`README.md:69-80`).
  - Built-in eval harness with rubric-based scoring and benchmark history for comparative model testing (`evals/run_eval.py:91-113`, `evals/lib/core.py:306-405`).

- **Limitations:**
  - Orchestration is mostly declarative prompt policy; there is little hard runtime enforcement of agent transitions or task state integrity.
  - “Agents” are role prompts, not isolated concurrent worker processes with explicit IPC/state machine.
  - Tool availability is assumed by frontmatter declarations; capability negotiation is weak outside adapter text.
  - Limited production observability/reliability mechanisms (retry logic, checkpoint recovery, deterministic traces) beyond eval scripts.

- **Research relevance:**
  - Useful evidence of **prompt-programmed hierarchical MAS behavior** without heavyweight orchestration frameworks.
  - Demonstrates how portable “agent suites” can be implemented as reusable skill artifacts across heterogeneous LLM CLIs.
  - Provides an empirical evaluation scaffold for comparing model adherence to role-specific protocols and rubrics.
  - Relevant for studies on tradeoffs between soft prompt governance vs. hard-coded orchestration in multi-agent workflows.
